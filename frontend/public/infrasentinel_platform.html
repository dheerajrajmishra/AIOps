Prompt-to-DAG Feasibility & Architectural Boundary

Detailed technical breakdown addressing: "also tell which part is not possible"

What IS Possible & Handled Directly:
  • 1. Natural Language Intent Parsing: Extracting steps, intent (e.g. disk check, SQL check, ping URL), and mapping them to registered agent tool types from the Agent Inventory.
  • 2. Dynamic Branch Synthesis: Mapping phrases like "on failure call PIC" to onFailureStepKey, and "if healthy proceed to step 2" to onSuccessStepKey.
  • 3. Entity Parameter Extraction: Automatically identifying target hosts, drive letters (D:), URLs (https://...), port numbers (3389), and phone numbers (+1555...).
  • 4. DAG Graph Layout & Cycle Verification: Assigning canvas coordinates, generating nodes, validating that no infinite circular dependencies occur.
What is NOT Possible (Without Dedicated Backend LLM Service):
  • 1. Unbounded Zero-Shot Code Generation: If a user requests a tool that does not exist in the Agent Inventory (e.g., "Deploy Kubernetes Helm chart on AWS EKS"), client-side JavaScript cannot create new un-compiled backend C# DLLs on the fly.
  • 2. Firewall & Credential Validation at Prompt Time: A prompt cannot verify whether SQL Server passwords, SSH keys, or Twilio SIP tokens are valid prior to actual test execution.
  • 3. Arbitrary Multi-Lingual Complex NLP without LLM Backend: Pure client-side parsing relies on rule/keyword heuristics. Complex ambiguous prompts with nested conditional clauses require an LLM inference API (like Gemini / Azure OpenAI API) hosted in the ASP.NET backend.
  • 4. Direct OS Hardware Execution from Browser: Browser sandboxing prevents JavaScript from executing raw WinRM, PowerShell, or TCP socket handshakes directly; all executions must be proxied through the .NET backend API.
